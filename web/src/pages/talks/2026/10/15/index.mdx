## More nodes is not a fix

Scaling an inefficient run scales the inefficiency.

GPU idle **40%** of the step → 512 more nodes buys you 40% idle on 512 more
nodes. Same fraction, bigger bill.

> [!IMPORTANT]+ First question, before any change
> Is the GPU busy?

<Slide id="what-to-measure">

## Pick the number first

| Metric | What it tells you | Use it for |
| --- | --- | --- |
| **tokens/sec/GPU** | what you are paying | the headline |
| **step time** | decomposes into phases | debugging |
| **MFU** | how much machine is left | knowing when to stop |

The trap: **2× on a kernel that is 15% of the step is a 7% win.** Speed up
the thing that dominates, or do not bother.

<SpeakerNotes>
Amdahl, without naming him. Worth writing the arithmetic on the board if the
room looks unconvinced -- 0.15/2 + 0.85 = 0.925.
</SpeakerNotes>

{/*───────────────────────────────────────────────────────────────
6 · MFU, concretely
───────────────────────────────────────────────────────────────*/}

<Slide id="mfu">

## MFU: how much of the machine are you using?

$$\text{MFU} = \frac{\text{model FLOPs}}{\text{peak FLOP/s} \times \text{step time}}$$

Both per-device, so `world_size` drops out. Every rank does the same work.

Do not hand-derive the numerator. `ezpz` counts it with `FlopCounterMode`
(real ops, not $6ND$) and looks up the peak, computing Intel PVC dynamically:

```python
from ezpz.flops import estimate_model_flops, compute_mfu
flops = estimate_model_flops(model, input_shape)   # counted, not estimated
mfu = compute_mfu(flops, step_duration)            # peak auto-detected
```

AuroraGPT production chains: 20B at **17-22%**, 2B at **9-12%**. Bigger
model, better utilization, same machine.

> [!WARNING]+ Published MFU assumes dense transformers
> Your model probably is not one. Compare against your own baseline, not a
> paper.

<SpeakerNotes>
The 20B/2B inversion surprises people: the bigger model is "slower" in
tokens/sec/GPU and better in MFU, because bigger matmuls keep the XPUs busy.
Source: ATPESC deck, all-production-perf.svg.
</SpeakerNotes>

</Slide>

<Slide id="roofline">

## The ceiling: roofline

Arithmetic intensity (FLOP per byte) against achievable FLOP/s. Two regimes,
two different fixes:

- **Memory-bound** — left of the ridge. Fusion, precision, layout.
- **Compute-bound** — right of it. Bigger matmuls, better kernels.

Knowing which side you are on tells you which half of this talk applies.

<Slide id="torch-profiler">

## Instrument it

Four decisions, four flags:

| Decision | Why | Flag |
| --- | --- | --- |
| skip the warmup | step 1 is allocator + autotune | `--pytorch-profiler-warmup` |
| capture a few steps | 1 is noise, 100 is gigabytes | `--pytorch-profiler-active` |
| one rank | 2048 ranks × traces → Lustre | `--rank-zero-only` |
| pay for what you read | shapes/stack/memory cost | `--record-shapes`, ... |

Defaults: `wait=1 warmup=2 active=3 repeat=5`.

> [!IMPORTANT]+ Profiling the warmup is the classic mistake
> Step 1 is allocator churn and autotuning. It is not your training step.

9 · Cheaper instrumentation

<Slide id="lightweight-timers">

## Before you reach for the profiler

A profiler perturbs what it measures and hands you gigabytes to interpret. A
timer around each phase answers *which quarter of the step* in five minutes.

Often that is the whole answer.

```python
from ezpz.history import StopWatch
with StopWatch("fwd", iter=step):
    loss = model(batch)
```

`ezpz` also has `timeitlogit` (decorator, logs per-rank) and `History.update()`,
which is where the `dt= dtf= dtb= sps= tps= mfu=` log lines come from.

<SpeakerNotes>
Demo exactly one of these. Three ways to time a function is worse than one
that works.
</SpeakerNotes>

</Slide>

<Slide id="vendor-tools">

## Vendor tools

**`torch.profiler` says _which op_. The vendor tool says _why that op is
slow_** — occupancy, bandwidth, which collective algorithm got picked.

Most people never need this. Go here when the trace blames a kernel and you
cannot see why.

<Cols>
<Col>

**Aurora** · Intel Max 1550

```bash
module load frameworks/2026.1.0
unitrace -d -h \
  --chrome-itt-logging \
  --chrome-kernel-logging \
  -o utrace python step.py
```

</Col>
<Col>

**Polaris · Perlmutter** · NVIDIA

```bash
module load pytorch/2.13.0
nsys profile -t cuda,nvtx,osrt \
  -o step_trace \
  --force-overwrite true \
  python step.py
```

</Col>
</Cols>

> [!WARNING]+ Do not `module load pti-gpu`
> `frameworks/2026.1.0` already loads `pti-gpu/0.17.0` and puts `unitrace`
> 2.3.0 on PATH. Loading `pti-gpu/1.0.1-rc1` on top breaks torch outright:
> `ImportError: libpti_view.so.0: cannot open shared object file`.

<SpeakerNotes>
unitrace ran on Sunspot (byte-identical stack to Aurora, rc=0); nsys ran on
a Perlmutter login GPU, 2.1 MB .nsys-rep. ncu is compute-node only -- on a
shared node the driver refuses counters. Trace selectors drift between nsys
versions: Polaris 2025.5.1 has cuda-hw, Perlmutter 2026.2.1 has cuda-sw and
nccl. cuda,nvtx,osrt is valid in every build checked, which is why it is the
one on the slide.
</SpeakerNotes>

</Slide>

<Slide id="annotation">

## Name your own phases

A vendor timeline shows kernels. **Annotation** makes it show *your* phases.

| | NVIDIA | Intel |
| --- | --- | --- |
| API | `torch.cuda.nvtx` | `torch.profiler.itt` |
| `range_push` / `pop` | yes | yes |
| `range_start` / `end` | yes | **no** |
| on the other vendor | **raises** | no-ops |

```python
nvtx = torch.cuda.is_available()
push = torch.cuda.nvtx.range_push if nvtx else torch.profiler.itt.range_push
pop  = torch.cuda.nvtx.range_pop  if nvtx else torch.profiler.itt.range_pop
```

> [!NOTE]+ Annotate once, behind a shim
> NVTX **raises** on XPU — `RuntimeError: NVTX functions not installed`. ITT
> no-ops on CUDA. So the shim only has to guard one direction.

`ezpz` has the profiler wrapper but **no annotation** — `record_function` is
imported-and-commented at `profile.py:49`. This is the gap.

<SpeakerNotes>
Verified both reach the trace, which is the claim that matters. Perlmutter
`nsys stats --report nvtx_sum` showed :forward, :backward, :optimizer and
train_step_0..4 alongside real CUDA kernels. Sunspot unitrace JSON contained
the same ranges. --chrome-itt-logging is the flag that makes ITT ranges land.
</SpeakerNotes>

<SpeakerNotes>
Aurora is the primary target; Polaris and Perlmutter are here because
attendees have allocations on them and the portable layer above genuinely
works on all three.
</SpeakerNotes>

</Slide>

<Slide id="portability">

## One setup function, three schedulers

| Machine | Device | Activity | Sorts by |
| --- | --- | --- | --- |
| **Aurora** | Max 1550 | `XPU` | `self_xpu_time_total` |
| **Polaris** | A100 | `CUDA` | `self_cuda_time_total` |
| **Perlmutter** | A100 | `CUDA` | `self_cuda_time_total` |

`ezpz` probes the device and picks both. `profile.py` is **byte-identical**
across machines (md5 verified) — no user branching.

The *launch* is not identical, though. Verified on Polaris:

```bash
export HTTP_PROXY=http://proxy.alcf.anl.gov:3128   # ALCF compute: no internet
source <(curl -fsSL https://ezpz.cool/utils.sh)
ezpz_setup_env && ezpz_install                     # install is a SECOND step
ezpz launch python3 -m ezpz.examples.profiler --profile --rank-zero-only
```

> [!WARNING]+ Three things that bite
> **No internet on ALCF compute** — the `curl` fails silently, then
> `ezpz_setup_env: command not found`. **The venv is named from `cwd`** — so
> `cd` into a project dir and you get a different, empty environment.
> **`--hf-limit`** defaults to no limit: ~6 min of tokenizing before step 0,
> which looks exactly like a hang.

Measured on Polaris, job 7670657, 1 node / 4x A100-SXM4-40GB, tp=2

## Reading a trace

`--profile` drops `torch-profiler-rank0-step{N}-{timestamp}.json`. Open it in
[Perfetto](https://ui.perfetto.dev) or `chrome://tracing`.

CPU rows on top (what Python asked for), device rows below (what ran). A
**gap in the device row is the GPU waiting.**

A real one, from the job behind this talk — Aurora, 2 nodes, 12 tiles:

| | |
| --- | --- |
| trace events | **373,458** |
| XPU kernels | 11,247 across 48 streams |
| device time | 115.0 ms |
| busiest stream | **5.9% busy, 94.1% idle** |
| gaps over 2 ms | **87** |
| largest gap | **9.5 ms** |

> [!IMPORTANT]+ That is the whole talk in one row
> Not a warmup artifact — the 87 gaps are spread through the run. This job
> is starved, and no amount of extra nodes fixes it.

<Slide id="fix-data">

## Fix: data stalls

Usually the cheapest big win, and the one teams skip because it is not the
interesting part.

- **Workers, prefetch, pinned memory** — the boring three, in that order
- **Many small files** is a metadata problem, not a bandwidth problem
- **Lustre does not like you** — one `stat()` storm × 50k ranks

> [!NOTE]+ Same failure as `import torch` at scale
> The fix is not a faster filesystem. It is not hitting the filesystem from
> every rank. See [`ezpz yeet`](https://samf.sh/posts/2026/05/01/).

Measured on Aurora, 8 → 4096 nodes: per-node env cost **8.7 s → 0.18 s**
(48×). Full-scale pre-launch **12.5 min**, first step at **16 min**.

</Slide>

{/*───────────────────────────────────────────────────────────────
14 · Communication
───────────────────────────────────────────────────────────────*/}

<Slide id="fix-comms">

## Fix: communication

- **Overlap** — the framework probably already does it; confirm in the trace
  before tuning anything
- **TP across nodes** is usually the bug, not a tuning problem

Keep `TP` on-node. `DP` is nearly free; `TP` is chatty.

**Turn the logs on before you tune anything:**

| | Aurora | Polaris · Perlmutter |
| --- | --- | --- |
| verbosity | `CCL_LOG_LEVEL=info` | `NCCL_DEBUG=INFO` |
| narrow it | — | `NCCL_DEBUG_SUBSYS=INIT,COLL,NET` |
| one file per rank | — | `NCCL_DEBUG_FILE=nccl.%h.%p.log` |
| who hung | `TORCH_NCCL_DESYNC_DEBUG=1` | same |

> [!IMPORTANT]+ Aurora ships quieter than the library default
> oneCCL defaults to `warn`; the setup lowers it to `ERROR`. You are getting
> *less* diagnostic output than the library would give you.

<SpeakerNotes>
Verified live by strings against the installed libs: oneCCL 2022.1.0 on
Aurora, NCCL 2.28.3 Polaris, 2.29.2 Perlmutter. Aurora arrives with 31
collective vars pre-set; Polaris arrives with ZERO -- that contrast is worth
saying out loud. TORCH_NCCL_DESYNC_DEBUG is the highest-value one: it prints
"[0,1,2,...] joined but didn't finish collective #39", which answers "did a
rank die or is the network stuck" in one line.
</SpeakerNotes>

</Slide>

<Slide id="fix-kernels">

## Fix: kernel efficiency

- **Mixed precision** — verify you got it; `bf16` in the config is not proof
- **`torch.compile`** — helps often; on AuroraGPT MoE it cost **26% of throughput**
- **Fused attention / optimizer** — usually free, check availability per device
- **Shapes** — pad to the tensor-core multiple

> [!WARNING]+ `torch.compile` is not free
> Compile time is real, and it does not always pay back. Measure it like
> anything else.

Measured: `moe_500m`, Aurora, 2 nodes / 24 tiles, 2026-04-13. TPS 11,200 →
8,316; TFLOPS 25.22 → 18.70; MFU 8.46% → 6.27%. All three agree on **-26%**,
which is the same thing as **+35% step time** — quote one, not both.

Compile also used **2.2× less memory** (8.44 → 3.78 GiB). A real trade.

<Slide id="failure-tax">

## The other way you lose GPU-hours

Everything so far assumed the run finishes. At scale it does not.

A crash at step 1,900 of 2,000 with a 100-step save interval costs you the
recompute, the restart, and the queue wait. None of it shows up in a profile.

> [!IMPORTANT]+ Throughput you never used is the same as throughput you never had
> An 18% MFU run that dies at 90% is a 0% MFU run.

<SpeakerNotes>
This is the bridge from "make the step fast" to "make sure the steps you paid
for survive." Keep it to one slide -- ATPESC covers the full failure story.
</SpeakerNotes>

<Slide id="auto-retry">

## `ezpz launch --auto-retry`

On a non-zero exit, scrape the log for known bad-node signatures, retire the
named host, rotate in a spare, relaunch. No babysitting.

```bash
ezpz launch --auto-retry --nhosts 8 --spare-nodes 2 -- \
  python3 -m ezpz.examples.fsdp_tp --model debug \
    --ckpt-dir ./ckpts --save-interval 100 --train-iters 3000
```

Catches: watchdog kill (124), walltime-racing crashes (143), Aurora PALS
shepherd-9, gloo peer-closed, and zero-progress hangs.

> [!WARNING]+ No spare, no retry
> Every retryable verdict is gated on `has_spares`. If `--np` eats the whole
> allocation there is nothing to rotate in and the run ends `EXHAUSTED`.
> Size with `--nhosts` and leave `--spare-nodes`.

<Slide id="async-ckpt">

## Checkpointing without paying for it

Sync save blocks training. Async stages to CPU, fans out in a background
thread, stamps `.complete` last.

| Model | Ckpt | Sync stall | Async stall | |
| --- | --- | --- | --- | --- |
| `agpt-2b` | 23 GB | 3.75 s | **1.05 s** | 3.6× |
| `agpt-20b` | 232 GB | 23.57 s | **5.4 s** | 4.4× |

```bash
python3 -m ezpz.examples.fsdp_tp \
    --ckpt-dir /shared/ckpts --async-ckpt \
    --ckpt-stage-dir /tmp/ezpz-ckpt --save-interval 100
```

> [!NOTE]+ Two dead ends got there
> A 5.18 s blocking drain that no metric recorded, then a marker stamped a
> full interval late — async was durable but not *resumable*. The fix probes
> on MPI's own communicator, not the training group, so it cannot deadlock
> against the gradient all-reduce.

[ezpz.cool/guides/checkpoint-restart](https://ezpz.cool/guides/checkpoint-restart/)

<SpeakerNotes>
The dead ends are the interesting part: both were invisible to the metrics
being logged at the time. Same lesson as the rest of the talk -- instrument
the thing you actually care about, or you will optimize a number that is not
the cost. 20b measured on 4 Sunspot nodes with --meta-init; memory went from
OOM at >64 GB/tile to ~14 GB/tile.
</SpeakerNotes>
