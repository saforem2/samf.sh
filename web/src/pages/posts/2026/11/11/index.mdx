[`torch-hammer`][torch-hammer] is an HPE-maintained GPU benchmark suite. It runs 9 workloads, from batched GEMM and stencil PDEs to sparse matmul. Telemetry uses `NVML`, `ROCm-SMI`, and `xpu-smi`. It writes CSV and HTML fleet reports and aggregates multi-GPU results with `multiprocessing.spawn`. One codebase supports `CUDA`, `ROCm`, `XPU`, and `MPS`.

[torch-hammer]: https://github.com/HPE/torch-hammer
[alcf]: https://www.alcf.anl.gov

## Results

Both completed runs used the same 9 benchmarks, `--stress-test`, and HBM-scaled sizing. Aurora and Polaris were queued in `debug` behind reservations when this snapshot was recorded.

PVC Max 1550 measured 2,028 GFLOP/s on Sparse MM; A100 measured 243 GFLOP/s, an 8.4× difference on this unstructured sparse workload. A100 led the other reported benchmarks or tied Batched GEMM.

Neither system completed 3D FFT. XPU returned an MKL DFT "unimplemented" error for the configured shape. Sirius ran out of memory at 11.75 GiB under stress fill on its 40 GB GPU; earlier benchmarks already held about 30 GiB.

Sirius defaults to Python 3.6, which raises a `SyntaxError` on `from __future__ import annotations`. It has no `mpirun`, `srun`, or `pbsdsh`, and the report tool also fails under Python 3.6. The run used `miniconda3/envs/cu122-pt221` with Python 3.11 and `torch` 2.2. A single-node `--all-gpus` fallback uses `torch.multiprocessing.spawn` to run on all 4 A100s.

The same PBS template works on the larger systems with per-system account, queue, and filesystem values. Each host uses one `rsync` staging step for `torch-hammer.py`, `reports/`, and `config-examples/` in `~/thammer-staging`.

## How the run is structured

Every job does the same four phases:

1. Single-GPU quick: all 9 benchmarks at small sizes with `--device-index 0`. This checks the run and exercises the CSV, JSON, and HTML report paths.
2. Single-GPU stress: all 9 benchmarks with `--stress-test`, sized to fill about 50% of free HBM. The memory benchmark measured `0.3 GB/s` before the sizing fix and `27.7 GB/s` after. The earlier run used a 4 KiB buffer and measured `randint` overhead.
3. Per-node all-GPUs: the `gemm`, `conv`, `einsum`, and `memory-traffic` subset under stress. One `mpiexec` rank runs per node and starts the node's GPUs.
4. Reports: `hammer_report.py` reads each CSV and JSON artifact. A fleet rollup reads `all-benchmarks/`.

Phase 3 is what produces the fleet verdict. Mixing quick + stress CSVs in one directory gives a spurious `0/N OUTLIER` report (different problem sizes) — isolated per-phase outputs are the correct inputs to the fleet report.

## Reproducing the runs

- Stage `torch-hammer.py`, `reports/`, and `config-examples/` in `~/thammer-staging` on each host.
- Set the system account, queue, filesystem, environment, and MPI launcher in the PBS template.
- Keep report inputs separated by phase. Mixing quick and stress CSVs produces a `0/N OUTLIER` result because the problem sizes differ.
- Run `hammer_report.py` on each single-GPU, stress, and fleet artifact.
